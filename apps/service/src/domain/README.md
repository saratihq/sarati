# The constitution — domain invariants and where they are enforced

Every rule below is LOAD-BEARING. Each has exactly ONE definition site and at
least one NAMED test that fails loudly if the rule is violated. **Changing a
rule is a deliberate amendment that says so** — never a drive-by edit. If you are
about to re-declare one of these constants or re-answer one of these questions
locally in another file: stop, import the definition instead.

| 1 | Version numbers are PER-BRANCH (`UNIQUE(workflow_id, branch_id, version_number)`, next number under a branch-row `FOR UPDATE` lock); a branch's first own commit is its v1 — the fork point is inherited, not copied. **Resolving a version has ONE site** (`VersionsReadService.resolveVersion`): a reference is an id, or a number WITH its branch — a bare number matching several branches RAISES, and an unresolvable branch name raises, because an unfiltered `findOne` would return whichever branch the database handed back | `workflows/versions-write.service.ts` (insertVersion), `workflows/versions-read.service.ts` (resolveVersion), DB constraint | `invariants.e2e-spec.ts` "per-branch numbering"; `mcp-diff.e2e-spec.ts` (id resolves where the bare number is refused); `version-rollback.e2e-spec.ts` (rollback refuses the ambiguous number) |

| 3 | **A no-diff commit mints nothing** — content-equal to the head returns the head with `no_changes`. **Nor does a merge the target already contains**: a source whose head is in the target's history (merge parents included) has nothing to merge, so the branches page refuses it (`nothing_to_merge`, and the branch is kept) and no review can be opened for it (`nothing_to_review`) | `versions-write.service.ts` commit (diff vs head via `ir/diff.ts`); `workflows/branch.service.ts` `historyContains`, used by `mergeBranchIn` and by opening a review | `invariants.e2e-spec.ts` "no-diff commits mint nothing" + "a merge the target already contains mints nothing, through BOTH entry points"; `review-nothing-to-merge.e2e-spec.ts` |

| 9 | Trigger resolution: an env-scoped webhook fires its env's PINNED version. **The trigger SOURCE is the version-doc trigger node under the env pointer** (per-`(workflow,env)` intake resolves env pointer → pinned version → the version's trigger node → run — never fans out), **not a side-channel row**. | 11 | **Trigger activations are DERIVED STATE**: the live schedule/poller/subscription set is the idempotent reconciliation of `DESIRED = ⋃ env-pointers × version-doc trigger nodes` against `ACTUAL = runtime_trigger_activations`. Only an env-pointer move (promote/unpromote/publish/restore) or a slot change alters an activation — **never a commit** (reinforces #2). **Amended 2026-10-09:** what is LIVE is recorded apart from what is desired (`runtime_trigger_activations.materialized`, written only once a teardown and a stand-up have both succeeded), and the planner compares desired against it: the cursor/subscription is kept across a promote IFF the desired kind, trigger type, resolved connection, paused state and props (vault `deepEqual`, invariant #4) equal what is recorded as live and the row's last apply finished — so a change outside those (a canvas-position nudge, a downstream step) keeps it. | 12 | **Error-output routing**: a node's error successors ride `port_type "error"` edges; the compiler lowers them into that node's `onErrorBranch` (the main flow is unchanged when no error edge is present), and the interpreter runs the error lane **iff the node throws** — in place of its main successors, **never both lanes**. The error edge is a structurally DISTINCT edge to `computeDiff` AND to `applyDiff`/merge `keyOf` — all three key edges by the endpoint tuple incl. `port_type` ( aligned applyDiff + merge, which previously keyed by the `id` label and collapsed a main+error pair; invariant #4/#13), so a rename/merge can never collapse a `main` and an `error` edge between the same nodes | `compiler/compile-ir-dag.ts` (error-lane peeling → `onErrorBranch` nested sub-plan; S4) + `runtime/base-plan-interpreter.ts` (`executeAction` error lane) | `invariants.e2e-spec.ts` "invariant 12: error output routes the error lane, never both, as a distinct edge" |
| 13 | **Node & edge identity is NATIVE**: a node `id` is a caller-assigned STABLE identifier (client canvas / composer `add_node`, format `NODE_ID_RE`) — identity, INDEPENDENT of the display `name`. So a rename keeps the id and diffs as a first-class `rename_node` op on that id (never an add+remove churn), and field conflicts key on that stable id (#5). The add+remove re-pairing **rename-detection heuristic is presentational-only and OFF by default** — it never feeds `applyDiff`/merge (merge runs `computeDiff` with detection OFF; a collapsed rename could corrupt it). Edge identity for diff/merge is the endpoint TUPLE `(source_node_id, source_port, target_node_id, target_port, port_type)` (`edgeKey`), NOT the edge's `id` label — enforced in `computeDiff`, `applyDiff` (`REMOVE_EDGE` by tuple), AND merge `keyOf` (`edgeId` deliberately omits `port_type`, so a main+error pair SHARE an id — id-keying would collapse them, tuple-keying never does). So a `main` and an `error` edge between the same nodes never collapse (reinforces #12) and a branch/case/loop-port edge is distinguished by `source_port` | `ir/diff.ts` (`edgeKey`, `applyDiff`, `detectRenamePairs`; name-change → `rename_node`), `ir/merge.ts` (`keyOf`), `compose/apply-ops.ts` (`NODE_ID_RE`, `edgeId`) | `ir/native-diff-merge.spec.ts` "node identity & rename" + "the rename-detection heuristic … is presentational and OFF by default" + "merge uses rename-detection OFF" + "edge identity" + "edge identity is the TUPLE" (same-id error edge survives a main removal; main+error same-nodes both land) |
| 14 | **Agent tool binding is edge-native**: a tool is a `port_type: 'tool'` edge from an `orchestr:agent` node to the bound tool node (any action, or a first-class `orchestr:call_workflow` sub-workflow). The compiler PEELS those edges into the agent step's `tools[]` (never a param blob) — the tool targets LEAVE the structural main flow (like a loop body / error lane) and never reconverge — and the `tool` edge is a structurally DISTINCT edge to `computeDiff` / `applyDiff` / merge `keyOf` because `port_type` is in the endpoint tuple key (reusing #13), so a `tool` and a `main` edge between the same nodes never collapse and an added/removed/re-pointed tool is a first-class reviewable diff | `compiler/compile-ir-dag.ts` (`AGENT_TOOL_PORT_TYPE = 'tool'` + the tool-edge peel beside the loop-body peel) + the existing `edgeKey` (`ir/diff.ts`) / `keyOf` (`ir/merge.ts`), no change | `invariants.e2e-spec.ts` "invariant 14: a tool edge binds a tool, distinct from a main edge, never collapses" + `ir/native-diff-merge.spec.ts` "a tool edge binds a tool, distinct from a main edge" |
| 15 | **A protected branch only takes change through an approved review**: merge is checked in `mergeBranchIn` — the ONE merge implementation (#5) — so the branches page inherits it rather than each caller re-deciding; and `commit` refuses outright, because a gate only on merge is walk-around-able by editing the branch directly. `rollback` deliberately still lands: it restores an existing version and is the documented recovery path. **Amended 2026-10-08:** the failing-test rule moved into `mergeBranchIn` too (`BranchService.latestFailingTest`, reading `review_test_results`, where every test is kept by the two versions it tested and outlives its review and branch) — a protected target refuses while the LATEST DECISIVE test of exactly the current heads, from any review, failed; a newer passing test lifts it, a test where the target failed too decides nothing, a tie fails closed, and a test of other versions or no test never blocks. The review detail shows the same answer (`BranchService.testBlockingMerge` → `merge_blocked_by_test`) — because the branches page used to skip it, so the same change was refused from a review and accepted from the overview's Merge into main. The reviews path keeps only its own stricter precondition (THAT review must be approved). An approval may not come from the review's own author **where another member exists** — otherwise the gate is self-satisfiable; a workspace with nobody else to ask is exempt so it cannot deadlock. **Amended 2026-10-09 (owner):** a protected branch takes only content a review and a test could see. An approval covers the source head it was given on (`review_approvals.source_version_id`, `BranchService.approvalStanding`), so a later commit needs approving again (`409 approval_stale`, `reason` `moved`, or `unversioned` for an approval given before approvals recorded a version), and one given on a head the reviewer was not shown is refused (`409 review_moved`); a merge into it never resolves conflicts (`409 protected_merge_conflicts`, resolutions refused too) — they are resolved on the source by taking the target's changes (`POST …/branches/:name/update`), which a protected branch never takes (`409 branch_protected`); it cannot be deleted while protected (`409 branch_protected`), so it cannot be recreated unprotected; a rollback to the head's own content mints nothing, and a rollback restores only a version the branch itself once held (`409 version_orphaned`), so a deleted branch's work never lands by rollback; and the failing-test rule reads the heads' CONTENT, not their ids — a decisive test of any version pair `computeDiff` finds equal to the heads counts (`BranchService.pairsWithContentOf`), superseding "exactly the current heads" above, so failing content put back under new version ids is refused again | `workflows/branch.service.ts` `mergeBranchIn` | `invariants.e2e-spec.ts` "a protected target refuses any merge no approved review authorised, through BOTH entry points" + "a protected target refuses a merge while the latest test of its heads is failing, through BOTH entry points" + "a protected target takes only what an approval covered, never conflicts resolved while merging, and cannot be deleted"; `domain/single-definition-sites.spec.ts` "only mergeBranchIn decides a merge on a pre-merge test"; `review-test-results.e2e-spec.ts` (kept by versions, latest decisive wins, ties fail closed, outlives its review and branch, follows content not version ids, an approval of an unseen head refused, a pre-version approval asked again); `workflows-write.e2e-spec.ts` (a deleted branch's version never rolled back onto main, a protected branch takes no update); `review-self-approval.e2e-spec.ts` (all three: blocked with a teammate, allowed solo, rejection unaffected) |

Rules of the vault:

- `src/ir/` imports nothing outside `src/ir` + `src/common` (dependency-cruiser: `moat-ir-is-pure`).
- `src/compiler/` imports only compiler/ir/runtime/common (`moat-compiler-bounded`).
- Every NEW invariant lands here with its definition site and its named test, in the same change.
- The trigger predicate `isTriggerNode` has ONE definition site (`compiler/compile-ir.ts`); the reconciler + compiler import it, never re-declare it. Guarded by `domain/single-definition-sites.spec.ts`, which exists because `compose/apply-ops.ts` was once found carrying a divergent private copy that missed the `…_trigger` suffix — so the composer refused to retype a node the rest of the system treats as the trigger. **Documented-but-unguarded is how that drift happens: every one-definition-site rule needs a test, not just a row.**

The whole table is enforced by `test/invariants.e2e-spec.ts`, `domain/single-definition-sites.spec.ts` and the `moat-*` rules in `.dependency-cruiser.cjs` — all of which run under `pnpm check`.
